# Desktop UI internationalisation (i18n)

The desktop app (`apps/desktop`) ships in two languages. Everything the user can
read — navigation, buttons, labels, placeholders, `aria-label`s, empty states,
error text — comes from a message catalog; nothing is hardcoded in a component.

## 1. Supported locales

| Locale | Native name | Role |
| --- | --- | --- |
| `en-US` | English | Source of truth for the message schema; **fallback** locale |
| `zh-CN` | 简体中文 | Second shipped locale (also the target for `zh`, `zh-TW`, `zh-Hans-*`) |

The picker is in **Settings → Language** (语言). Option labels are always the native
names, so the control stays usable while the current language is the one being
replaced.

## 2. Files

| Path | Responsibility |
| --- | --- |
| `src/i18n/locales/en-US.ts` | English catalog. Exports `MessageSchema = typeof enUS`. |
| `src/i18n/locales/zh-CN.ts` | Chinese catalog, annotated `: MessageSchema`. |
| `src/i18n/locale.ts` | Pure locale functions: detection, storage, resolution, `<html lang>`. No Vue, no i18n import — unit-testable without a DOM. |
| `src/i18n/index.ts` | The single `i18n` instance, `setLocale()`, `statusLabel()`, `formatEventTime()`. |
| `src/i18n/errors.ts` | Turns a caught error into a localised sentence (see §6). |
| `src/test/setup.ts` | Installs the instance into every mounted test component and pins the test locale to `en-US`. |

`main.ts` installs it once: `createApp(App).use(i18n).mount("#app")`.

## 3. How the starting locale is chosen

`resolveInitialLocale()` applies this precedence — the user's explicit choice
always wins over the operating system:

| Stored value | `navigator.languages` | Result |
| --- | --- | --- |
| `zh-CN` | `["en-US"]` | `zh-CN` |
| `en-US` | `["zh-CN"]` | `en-US` |
| absent | `["zh-CN"]` | `zh-CN` |
| absent | `["zh"]` / `["zh-Hans-CN"]` / `["zh_TW"]` | `zh-CN` |
| absent | `["en-GB"]` | `en-US` |
| absent | `["fr-FR", "zh-CN"]` | `zh-CN` (unsupported tags are skipped) |
| `klingon` (corrupt) | `["zh-CN"]` | `zh-CN` |
| `""` / broken JSON | `["fr-FR"]` | `en-US` |

Details that matter:

- The choice is stored in `localStorage` under `deskweave.locale`. There is no
  other settings store in the app (the Runtime card in Settings is read-only), so
  this is the only place a UI preference is persisted.
- Reading or writing storage never throws: private mode, a denied origin or a
  quota error degrade to "no remembered choice" and the app still starts.
- A stored value that is not one of the supported locales is treated as absent —
  it is never rendered, and it is never passed to `Intl`.

## 4. Switching language

`setLocale(locale, { persist })` does three things: sets the reactive locale,
updates `<html lang>`, and (unless `persist: false`) writes the choice.

Because every component reads `t()` during render, the change is visible
immediately in the mounted tree — no reload, no remount, no refetch of runtime
state. `src/i18n/language-switch.test.ts` asserts exactly that: the nav relabels
in place, the five nav buttons are still the same five, and the language of a
*visible error banner* changes too.

`persist: false` exists for tests only.

## 5. Using messages in components

```ts
import { useI18n } from "vue-i18n";

const { t, n, d } = useI18n();
```

- Prefer `t("references.emptyTitle")` in the template; keys are namespaced by
  screen (`app`, `overview`, `tasks`, `references`, `logs`, `settings`,
  `adapters`, `common`, `status`, `errors`).
- Dynamic keys (built from a runtime value) must go through a helper that checks
  `te()` first — see `statusLabel()` and `taskErrorText()`. A missing key must
  never surface as `references.someKey` in the UI.
- `$t` in templates is **not** used: the Composition API keeps the source of truth
  in one place and avoids the legacy global-injection path.

### Dynamic values, plurals, numbers, dates

| Kind | Form | Example |
| --- | --- | --- |
| Plain interpolation | `t(key, { name })` | `t("references.updatedAt", { timestamp })` |
| Plural | `t(key, { count }, count)` | `"{count} candidate \| {count} candidates"` |
| Number | `n(value, "integer" \| "decimal1")` | `n(4, "decimal1")` → `4.0` |
| Date | `d(value, "short")` | only for event times — see below |

Chinese has a single plural form, so its message is written once and vue-i18n
uses it for every count.

**Timestamps:** record metadata (`created_at`, `updated_at`) is rendered as the
ISO 8601 string the runtime produced. It is cross-referenced with logs and the
database, where `Oct 20, 10:01` is less precise, not more. The one time the user
*acted* on — the confirmation — is formatted for humans through `d()`.

**Sizes:** `formatBytes()`/`sizeLabel` use `n()` for the numeric part and `common.units.*`
for the unit, so `2048` bytes renders as `2 KB` in both locales.

## 6. Errors

Errors are kept **structured** (`{ kind, code, detail }`) instead of pre-rendered
strings, so a banner that is already on screen re-renders in the new language.

| `kind` | Source | Rendering |
| --- | --- | --- |
| `unavailable` | `RuntimeUnavailableError` (transport) | `errors.unavailable` + `({detail})` |
| `api` | `RuntimeApiError` (runtime said no) | `errors.codes.<code>`; unknown code → `errors.codeUnknown` naming the code |
| `unknown` | anything else | `errors.unknown` with the raw message |

`detail` is the transport/runtime diagnostic (HTTP status, the server's own
sentence, a URL). It is deliberately **not** translated: it is evidence, and it is
what the user pastes into a bug report. The localised sentence always comes first;
the detail is appended, never substituted.

Task-level failures (`task.error.code`) use the same code map through
`taskErrorText()`. For a code with no mapping the runtime's own message is shown —
better an untranslated fact than a fabricated explanation.

Task and health **states** are a separate namespace, `status.*`. The state value
itself is never rewritten: `StatusBadge` renders the localised label but keeps
`data-status="waiting_for_confirmation"` in the DOM, so the protocol vocabulary
stays inspectable. Unknown states render verbatim.

## 7. What is deliberately not translated

| Content | Why |
| --- | --- |
| Task names, search queries, adapter/capability descriptions, `component.detail` | Runtime data, not UI copy. The runtime has no locale. |
| Ids, run ids, file paths, media types, `ReferencePlane` example, SHA-256s | Identifiers. Translating them would make them unsearchable. |
| `DeskWeave`, `DW`, `.blend`, `Blender` | Product and format names. |
| `created_at` / `updated_at` values | See §5. |
| Protocol vocabulary (`pending`, `read_only`, …) | Written to the database and to logs; only its *label* is localised, and `en-US` maps each value to itself. |

## 8. Adding a language

1. Add the code to `SUPPORTED_LOCALES` and its native name to `LOCALE_LABELS` in
   `src/i18n/locale.ts`.
2. Add the tag mapping in `matchLocale()` (which BCP 47 prefixes map to it).
3. Copy `locales/en-US.ts` to `locales/<code>.ts`, translate the values, and keep
   it annotated `: MessageSchema` — missing or extra keys fail `vue-tsc`.
4. Register the import in `src/i18n/index.ts` (`messages`, `numberFormats`,
   `datetimeFormats`).
5. Run `pnpm --filter @deskweave/desktop exec vue-tsc --noEmit` and the tests; the
   parity test in `src/i18n/locales.test.ts` walks both catalogs and fails on any
   key that exists in one and not the other.

Do **not** change `DEFAULT_LOCALE` when adding a language: `en-US` is the
documented fallback for every key.

## 9. Tests and commands

```bash
# from the repo root
pnpm --filter @deskweave/desktop test          # vitest run
pnpm --filter @deskweave/desktop exec vue-tsc --noEmit
pnpm --filter @deskweave/desktop lint          # eslint, --max-warnings 0
pnpm --filter @deskweave/desktop format:check  # prettier
pnpm --filter @deskweave/desktop build         # vue-tsc + vite build
```

| Test file | Covers |
| --- | --- |
| `src/i18n/locale.test.ts` | Tag detection, precedence, corrupt storage, throwing storage |
| `src/i18n/locales.test.ts` | Key parity, no empty strings, plurals, numbers, dates, unknown-key and unknown-status fallbacks |
| `src/i18n/errors.test.ts` | Code mapping in both languages, unknown code, detail preservation, task-level codes |
| `src/i18n/language-switch.test.ts` | In-place relabel of the running app, confirmation gate unchanged, error banner retranslated |
| `src/views/SettingsView.test.ts` | Picker contents, immediate effect, persistence, corrupt persisted value |

On Windows, run vitest through `node` with an upper-case `process.chdir()` (see the
repository notes) — otherwise every file fails during collection for reasons that
have nothing to do with the tests.

`scripts/ui_smoke.py` drives the built app in a headless browser and asserts
English copy. Because the UI now follows the host language (the Playwright
Chromium on this machine reports `zh-CN`), that script stores
`deskweave.locale = en-US` before the first navigation — the same precedence the
picker gives a user, not a test-only flag. If you add a locale, keep the pin or
make those assertions language-independent.

## 10. CSP constraint

`src-tauri/tauri.conf.json` sets a strict CSP with **no** `'unsafe-eval'`. vue-i18n
11 compiles messages to an AST and interprets it instead of generating code with
`new Function`, so it works under that policy. The built bundle was checked for
this: `dist/assets/index-*.js` contains zero occurrences of `new Function` and of
`eval(`.

Two rules follow:

- never add `'unsafe-eval'` to the CSP to make an i18n feature work;
- if a future version of the library starts evaluating message source, adopt a
  build-time precompilation step instead of relaxing the policy.

## 12. English copy that changed

Plural handling replaced the placeholder-style `(s)` suffix, which is why three
assertions in `src/views/ReferencesView.test.ts` changed with it:

| Before | After |
| --- | --- |
| `2 candidate(s)` | `2 candidates` |
| `1 object(s): …` | `1 object: …` |
| `1 candidate(s) could not be saved` | `1 candidate could not be saved` |

No behavioural assertion was relaxed: ids, counts, `data-test` hooks and the
"confirm is disabled until something is selected" rule are asserted exactly as
before.
